# RFC - pre-talk 架构与决策

## 三层闭环中的位置

| 层 | 时机 | 载体 | 接口 |
|---|---|---|---|
| 想清楚（本仓） | 沟通前 | 用户自己的 agent + pre-talk skill | 产出备谈卡 |
| 听懂对方 | 沟通中 | Rokid AI Glasses 智能体（平台全托管） | 卡内「眼镜开场白」经会前定锚态注入（设备端 v0.1.10+ / D11） |
| 复盘提高 | 沟通后 | 用户自己的笔记/周回顾 | 备谈卡留档比对 |

## 决策否案

**C1 为什么是 skill 而不是独立 App**
否掉：独立 App / 网站。理由：方法论对话即可完成，零 UI 依赖；skill 装进用户已有 agent，分发边际成本为零（fork/clone 即用）；独立 App 会把受众收窄为「愿意再装一个 App 的人」，与开源获星目标相反。

**C2 备谈卡为什么是 Markdown**
人机共读：用户自己能改，agent 能解析校验；可 diff 可留档，复盘时直接与实际对话比对；不引入数据库与格式锁。

**C3 眼镜通道：会前定锚态（设备端 v0.1.10 / D11，2026-11-22 落地）**
「听懂对方」（Rokid Agent Store 版）v0.1.10 起支持会前定锚：待机长按进入锚采集（纯 ASR、零 LLM 调用），说完停顿即定锚；锚文本（≤120 字）存设备侧状态机字段，逐结算单元建会话时注入 LLM 系统提示（动态后缀），再长按清除。备谈卡的「眼镜开场白」即定锚采集文本，卡契约不变。教训存档：初版曾宣称「口播开场白会被平台 LLM 当作对话上文」，与当时设备端单轮会话制（结算即销毁）不符，被外部 review 纠正——正确的通道是设备侧定锚态；本仓不宣称任何未经设备端代码验证的联动机制。

**C4 四步为什么是对话式而不是表单**
核心句靠筛除逼进（可剔除/可合并/排序低），表单会诱导用户直接填一句「口号」。对话式才能执行「删到剩那句删不掉的」工序。排序试金石（答不出第二重要，第一句是口号）同样只能在追问中生效。

**C5 License 为什么是 MIT**
方法论非原创（致谢黄执中/表达学院公开课），本仓是工程化；MIT 最大化可装配性，配合「装进你自己的 agent」定位。致谢与无隶属声明固定在 README，防误读为官方产品。
